# CPU-only production readiness

The upgrades below originally used rule-based CPU detection. An optional
pretrained CPU lens-proposal backend is now available through **AI assisted ·
experimental** front analysis; it uses an isolated environment, source-edge
refinement and geometry checks. The front-photo panel starts with AI assistance;
the API's unspecified-backend default remains standard detection. No model
training, cloud inference API or CUDA runtime is required. See the
[hybrid evaluation and limitations](RECONSTRUCTION_ROADMAP.md#independent-gate-not-achieved).
This is a staged reliability upgrade, not a claim of universal reconstruction.

## Engine 30: anatomy contract and product-local recovery

The `gemini` branch now includes a versioned eyewear part graph and geometric
audits, read-only editor audit API, persistent candidate evidence and review UI.
The graph separates observed/inferred/uncertain parts, preserves explicit arm
mirroring, excludes held-out/unapproved evidence and does not infer absent pads
from failed extraction. Original annotations without graph metadata still work.

Incomplete front extraction can retry in a guarded product-local studio crop,
then map coordinates back to the source photo. Existing paired-optics and support
detectors remain required; it is not arbitrary-background semantic segmentation.
Procedural freeform geometry remains in use, with no SKU-template catalogue.

Final verification: 285 backend tests passed and the frontend production build
passed. Novel synthetic shapes/offsets and negative images are regression tests,
not independently labelled unknown products. See
[implementation progress and verification](ANATOMY_IMPLEMENTATION_PLAN.md) and
[architecture and API contract](ANATOMY_ARCHITECTURE.md). Live browser acceptance
could not run because this session cannot bind a localhost server port.

## Engine 29: grey rim / dark lens landscape regression

The newly supplied 1298x618 photo originally returned no annotations. Dark-lens
thresholds absorbed the grey rim/bridge at higher brightness levels, and the
frame-proportion guard depended on square-photo margins. Recovery now finds a
stable three-threshold lens interval independently of higher thresholds that
merge hardware, and validates object proportions rather than blank margins.
Smaller inputs are attempted with the same positive-evidence checks.

Inspection also revealed a convex pad completion that filled a triangular
region of background. Large convex completions of concave rim residue are now
rejected. Dark pads are traced independently outside the lens masks at three
contrast levels, with nasal-region and stability checks. Unverified invisible
pad portions are not completed.

The supplied image detects front, both lenses, upper bridge opening and both
pad silhouettes at widths 324, 648, 1298 and 2596, including mirrored variants.
An additional test adds blank top/bottom margins and checks that object contours
remain consistent. These are regression derivatives of one product, not nine
unseen products or a generalization score. Inspect `artifacts/grey-sunglasses/`
after `.venv/bin/python scripts/verify_grey_sunglasses.py`.

## Implemented in engine 28

- Detection-only gain calibration from a verified uniform light border handles
  dim and mildly tinted catalogue backgrounds. Dark, textured or inconsistent
  borders are not forced white. Original uploads and material pixels remain intact.
- Rimless recovery tries weaker edge contrast levels when its original levels
  cannot establish paired lenses. Stability and support limits account for source
  pixel scale. Small inputs are attempted instead of rejected at 320 pixels.
- Independently supported bridge hardware is still required. Missing pads are
  explicitly reported and omitted, never filled with generic replacement pads.
- A CPU benchmark compares contours to independent source-space polygon labels,
  checks missing/invalid/out-of-bounds/duplicate parts, and reports quality and
  p95 elapsed time by frame family. Detection counts alone do not pass its gate.

## Run an independent product benchmark

Create a JSON manifest outside live project data. Paths are relative to the
manifest. `expected` contains manually reviewed polygons in original photo
pixels, not polygons generated by this detector. Include every required visible
part, including pads and hardware where relevant. Example schema:

```json
{
  "split": "unseen-products",
  "development_manifests": ["frozen-development.json"],
  "required_families": ["transparent-full-rim"],
  "cases": [{
    "sku": "merchant-product-001",
    "family": "transparent-full-rim",
    "view": "front",
    "path": "photos/product-001-front.png",
    "sha256": "ACTUAL_IMAGE_SHA256",
    "label_source": "independent-human",
    "label_reviewer": "INDEPENDENT_REVIEWER_ID",
    "expected": {
      "lens-left": [[10, 10], [30, 10], [30, 30], [10, 30]]
    }
  }]
}
```

The coordinates above illustrate the schema, not valid labels for a real photo.
Keep all views and resolution variants of a SKU in the same split. Do not tune
against the release holdout; maintain a separate development set. Include
rimless, semi-rimless, metal, transparent, opaque, sunglasses and shields with
different colours, shadows, reflections, pad types and resolutions. Repeated
derivatives test scale consistency, not unseen-product generalization.

```sh
.venv/bin/python scripts/benchmark_detection.py /absolute/path/holdout.json \
  --output artifacts/production/holdout-report.json \
  --min-iou 0.90 --max-boundary-fraction 0.01 \
  --min-family-pass-rate 0.95 --min-products-per-family 20 \
  --max-seconds 15 --gate
```

These are configurable example targets, not achieved scores or guaranteed SLAs.
Choose stricter boundary criteria for thin rims and targets appropriate to the
deployment CPU. The gate exits 2 on failure. It checks hashes and product/image
overlap against the supplied frozen development manifests and requires label
provenance. It cannot prove label independence, catch SKU aliases/near-duplicates
or inspect an unknown third-party training set. A small sample
passing a rate target is not statistical evidence of broad reliability.
The gate uses product-level pass rate: all required cases of a SKU must pass.
Twenty distinct products per family is a configurable initial minimum, not a
proof of generalization. Set `required_families` to every family the release
claims to support; an omitted family cannot be certified by this benchmark.

See [unknown-product roadmap](RECONSTRUCTION_ROADMAP.md) for local saved-upload
replay and the optional pretrained CPU candidate evaluator. Neither unlabelled
replay nor an operational `review-required` result is an accuracy pass.

## Still required before a production-readiness claim

1. Acquire and independently label a representative unseen-product dataset;
   establish minimum sample counts per family and actual correction rates.
2. Improve general foreground/part tracking beyond quiet light backgrounds,
   including clutter, strong reflections and severe arm overlap. Current
   calibration is deliberately restricted to verified light flat backgrounds.
3. Validate rendered geometry/materials against source views, separately from
   contour accuracy. This benchmark does not certify lens tint, logos, pad mounts,
   transparency, physical thickness or hidden construction.
4. Add targeted correction/extra-photo requests and evaluate merchant completion
   rates. Current suggestions remain unapproved and require review.
5. Load-test concurrent CPU jobs, set upload/resource/time limits, and validate
   storage backups, authorization and deployment health checks on the server.

At 320x320 the rimless regression recovers both lens perimeters and the bridge,
but only one pad is established. At 160/256 the same reference can still lack
enough continuous hardware evidence. Enlarging pixels does not recover missing
detail. Exact unseen hardware depth requires measurements, more views or CAD.
